Day 11 — Linux Log Analysis with journalctl

This lab uses two temporary systemd services on Kali Linux to show how to investigate a service failure and verify a successful run. The first service simulates a missing configuration and exits with status 1. The second represents a successful check after recovery and exits with status 0. Both runs are captured in the systemd journal.

1. Generate a failed run and a successful run

sudo systemd-run --unit=day11-failure --wait \
  /bin/sh -c 'echo "ERROR: health check configuration missing" >&2; exit 1'

sudo systemd-run --unit=day11-recovery --wait \
  /bin/sh -c 'echo "OK: health check completed"; exit 0'
Code What it does and why
sudo systemd-run Asks the system systemd manager to create a temporary service with elevated privileges. This lets you practice without writing a service file or changing an existing service.
--unit=day11-failure and --unit=day11-recovery Assign distinct service names so you can query the logs for each run.
--wait Waits for the command to finish and reports the result in the terminal.
Trailing backslash Continues the command on the next line so the invocation is easier to read.
/bin/sh -c '…' Runs the quoted command string in a shell so the shell can interpret the redirection and execute both commands.
echo "ERROR: health check configuration missing" >&2 Writes a simulated configuration error to standard error so the journal records a diagnostic message.
exit 1 Gives systemd a nonzero process status to record as a failure. The exit status determines the outcome.
echo "OK: health check completed" and exit 0 Write a success message to standard output and signal that the command completed successfully.

The semicolon inside each quoted command separates the message from the exit command. The two units model failure and recovery using separate runs.

2. Investigate the failure in the journal

sudo journalctl -b -u day11-failure.service --no-pager
Code What it does and why
sudo journalctl Reads the system journal with elevated permissions so system service entries are accessible.
-b Selects the current boot. This keeps earlier boots out of the results when investigating a run from this session.
-u day11-failure.service Selects entries associated with the failed unit so you can follow its start, output, and termination.
--no-pager Prints directly in the terminal, which makes the output easy to capture or pipe into another command.

The screenshot shows the simulated error message, status=1/FAILURE, and Failed with result 'exit-code'. The message describes the simulated cause. The systemd entries confirm how the process ended.

3. Save both runs as evidence

mkdir -p ~/linux-labs/day-11-journalctl-analysis

sudo journalctl -b \
  -u day11-failure.service \
  -u day11-recovery.service \
  --no-pager \
  | tee ~/linux-labs/day-11-journalctl-analysis/journal-evidence.txt
  • mkdir -p creates the evidence directory and any missing parent directories. ~ expands to your home directory.
  • Each -u adds a unit to the query. Including both gives you a single timeline with the failure and the successful run.
  • The pipe sends the journal output to tee. It displays the output and writes it to journal-evidence.txt. Running the command again replaces the text file.

Verified results

Check Observed evidence
Failed run status=1/FAILURE and Failed with result 'exit-code'
Successful run status=0/SUCCESS in the command output and Deactivated successfully in the journal
Combined query Both units appear in the output sent to journal-evidence.txt

Troubleshooting

  • No entries after a reboot. Run sudo journalctl --list-boots to check which boots are retained. If the previous boot is listed, use -b -1 to query it.
  • The failure unit name is already in use. If it is still listed as failed, run sudo systemctl reset-failed day11-failure.service before retrying. If you want clean evidence for a new run, use new unit names and update both journal filters.
  • The evidence file cannot be created. Confirm that the lab directory exists and that your user can write there. In the pipeline, sudo applies to journalctl, while tee runs as your current user.
